# Dogwood — TypeScript / WebAssembly bindings

Typed WASM bindings for [Dogwood](https://github.com/dogwood-policy/dogwood),
the Cedar-derived governance language for AI agents (temporal conditions +
information providers).

They wrap the same curated public surface of the `dogwood-language` crate that
the `dogwood` CLI drives, so you get the parser, validator, Cedar-lowering, and
the stateful authorizer callable from Node or the browser — returning real JS
objects with real `.d.ts` types, not JSON strings.

Two shapes are exposed, because hosts need both:

- **the batch operations** (`validate`, `lower`, `replay`, the schema checks) —
  policy-authoring and CI tooling: source strings in, report objects out;
- **the live authorizer** (`DogwoodAuthorizer`) — lower a policy set once, then
  feed events **as they happen** and get a decision per event, with temporal
  history accumulating across calls. This is the shape an agent gateway or MCP
  proxy actually needs; `replay` only answers the after-the-fact question.

## Layout

```
dogwood-wasm/
├── src/
│   ├── lib.rs        # the wasm-bindgen surface (batch ops + error projection)
│   ├── live.rs       # the live, stateful DogwoodAuthorizer
│   ├── ops.rs        # the frontend operations (verbatim from dogwood-cli)
│   └── error.rs      # miette -> structured diagnostic (verbatim from dogwood-cli)
├── pkg/              # ← generated by `npm run build` (git-ignored)
├── test.cjs          # batch-operation tests
├── test-live.cjs     # live-authorizer tests
├── example.ts        # strict-mode type-check of the generated .d.ts
└── package.json      # build / test / typecheck scripts
```

`pkg/` is **not** committed — it is generated, and `wasm-pack` writes a
`pkg/.gitignore` saying so. Build it with one command (below).

There is no CI job for this crate yet. `ci.yml` cannot cover it: the crate is a
`cdylib` for `wasm32-unknown-unknown`, so `cargo test --workspace` cannot
exercise it, and the real gate — the generated package loading and deciding
correctly under Node — needs the wasm target, `wasm-pack` and Node installed.
Until that job exists, `npm run verify` (below) is the check, run by hand.

## Build

Needs Rust ≥ 1.85 (the workspace is edition 2024), the wasm target, `wasm-pack`,
and Node ≥ 16.

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-pack          # or the official installer script

cd dogwood-wasm
npm run build                    # -> pkg/  (Node/CommonJS target)
npm install && npm run verify    # runtime tests + tsc --strict typecheck
```

Other targets: `npm run build:bundler` (Vite/webpack, ESM) and `npm run
build:web` (no bundler). Same source, same command shape.

## The batch operations

All take source **strings** and return typed report objects (mirroring the CLI's
`--format json`). Fatal errors are *thrown* (see [Errors](#errors)); non-fatal
findings come back in the report.

| Function | Purpose | Returns | Needs action schema? |
|---|---|---|---|
| `checkParse(src, …)` | parse + macro-expand; structural summary | `CheckParseReport` | no |
| `validate(src, actionSchema, …)` | lower to Cedar + type-check | `ValidateReport` | yes |
| `lower(src, actionSchema, …)` | lower to Cedar; emit artifacts | `LowerArtifacts` | yes |
| `replay(src, actionSchema, log, …)` | lower, then replay a `.log` trace | `ReplayReport` | yes |
| `checkActionSchema(src)` | validate a Cedar `.cedarschema` alone | `SchemaCheckReport` | (is the schema) |
| `checkEventSchema(src)` | validate an event-schema DSL alone | `SchemaCheckReport` | no |
| `checkProviders(json)` | validate a `providers.json` alone | `SchemaCheckReport` | no |
| `mcpToCedarSchema(manifestJson)` | Cedar action schema from an MCP `tools/list` manifest | `string` | no |

The trailing `eventSchema? / providers? / macros?` arguments are the optional
service-schema overrides (event-schema DSL text, provider declarations JSON,
macro-library text). Omit them for the defaults (the request/response event
convention plus the standard macro library).

```js
const dw = require("./pkg/dogwood_wasm.js");

const actionSchema = `namespace Drupe {
  entity User; entity Gateway;
  type ReadInput = { document: String, user: String };
  type ReadOutput = { content: String };
  action "Read" appliesTo {
    principal: [User], resource: [Gateway],
    context: { input: ReadInput, output: ReadOutput }
  };
}`;

const policy = `permit(principal, action == Drupe::Action::"Read", resource)
when { context.input.document like "*report*" };`;

console.log(dw.validate(policy, actionSchema).passed); // true
```

## The live authorizer

```js
const auth = new dw.DogwoodAuthorizer(policy, actionSchema);

const decision = auth.isAuthorized({
  action: "Drupe::Action::Read",          // qualified, id UNquoted
  kind: "request",                         // default; a decision point
  timestamp: Math.floor(Date.now() / 1000),
  principal: { type: "Drupe::User", id: "alice" },
  resource:  { type: "Drupe::Gateway", id: "gw1" },
  logged:  { input: { document: "quarterly report", user: "alice" } },
  context: { input: { document: "quarterly report", user: "alice" } },
  entities: [{ type: "Drupe::User", id: "alice", attrs: { dept: "eng" } }],
});

if (!decision.allowed) throw new Error("denied");
```

`isAuthorized` returns `undefined` for a **history-only** event (by default
anything other than `kind: "request"`): it updates temporal state but yields no
verdict. That is how a host records the `response` half of a call so later
policies can correlate against it.

`reset()` drops accumulated history and re-lowers; `decisionCount` is how many
decisions the instance has returned.

### Lifetime — you must free it

`DogwoodAuthorizer` is a wasm-bindgen class, so it owns memory on the wasm heap
(the lowered policy set plus the temporal history) that **JS garbage collection
does not reclaim**. A long-lived host that creates authorizers per request leaks
until the module is torn down. Free it explicitly, or bind it with `using` and
let the disposal protocol do it:

```ts
const auth = new DogwoodAuthorizer(policy, actionSchema);
try {
  /* … */
} finally {
  auth.free();
}

// or, with TypeScript >= 5.2 / a runtime supporting explicit resource management:
function decideOnce(event: EventInput): Verdict {
  using scoped = new DogwoodAuthorizer(policy, actionSchema);
  return scoped.isAuthorized(event)?.verdict ?? "deny";
}
```

Note that because the bindings now export a class, the generated `.d.ts`
declares `[Symbol.dispose]()`. Type-checking against it needs **TypeScript
≥ 5.2** and the `ESNext.Disposable` lib (or `target: "esnext"`); see
`tsconfig.json`. The batch operations are plain functions and have no such
requirement.

Note also that the natural instinct — one authorizer per request — is usually
wrong: it throws away the temporal history that makes the language worth using,
and pays the lowering cost every time. Lower once per policy set, and keep the
instance for as long as the history should live.

Four things are worth knowing, because getting them wrong is silent:

- **Timestamps are in seconds**, not milliseconds — a `within 1h` window is
  3600. Passing `Date.now()` inflates every window by 1000×, so `within 1h`
  would match only the last 3.6 seconds. Use `Math.floor(Date.now() / 1000)`.
- **`logged` and `context` are different datasets, not a convenience split.**
  `logged` is the durable temporal record future events correlate against;
  `context` is the ephemeral per-decision Cedar request context. A field both
  halves need — typically `input` — must be supplied in **both**. The frontend
  is deliberately explicit here, and so are these bindings.
- **Entity references are structured** (`{ type, id }`), never `Ns::Type::"id"`
  literals. The `id` is the *decoded* id and is escaped exactly once at the
  Cedar boundary, so an id containing `"` or `\` cannot be double-escaped (a
  real footgun of the literal-taking API). A test covers `ali"ce`.
- **A deny with a non-empty `errors` is a fail-closed failure**, not "policy
  said no". Evaluation problems (a provider that cannot run, a wrong-typed
  entity attribute) deny *and* report the cause; they are never thrown.

Values are JSON, with two tagged escapes for what JSON cannot express:
`{ __entity: { type, id } }` for an entity reference and
`{ __decimal: "1.50" }` for a decimal whose exact text matters (a JS number
round-trips `1.50` as `1.5`). Non-integer numbers become decimals.

### Known gap

The default event schema declares two top-level *scalar* logged fields,
`requestId` and `sessionId`. The frontend's public `EventBuilder` can only set
logged fields nested under a group (`field(group, name, value)`), and
`Event`'s fields plus `Event::from_parts` are `pub(crate)` — so those two
fields are **not reachable by any out-of-crate caller**. The `.log` parser sets
them because it builds `EventData` directly, inside the crate.

Consequence: a policy that pins on `requestId`/`sessionId` can be exercised
through `replay` (a `.log` trace) but not through the live authorizer. Closing
this needs a small upstream addition — a scalar-logged-field setter on
`EventBuilder` — not a change here.

## Errors

Every operation throws a real `Error` named `DogwoodError` on a fatal
parse/lower/schema failure. The human message is `error.message`; the structured
diagnostic (the CLI's JSON contract) is attached as `error.diagnostic`, typed as
`DogwoodDiagnostic` (`message`, `severity`, `code?`, `labels`, `help?`,
`related?`). Byte offsets in `labels` index the source string you passed in, so
you can underline the offending span.

```ts
import { validate, type DogwoodError } from "./pkg/dogwood_wasm.js";
try {
  validate("permit(", actionSchema);
} catch (e) {
  const err = e as DogwoodError;
  console.error(err.diagnostic.message, err.diagnostic.severity);
}
```

A malformed *event* (a bad `__entity` tag, say) throws a plain `Error` naming
the offending field.

## How the crate is put together

`ops.rs` and `error.rs` are copied **verbatim** from `dogwood-cli`, with only
`tsify` derives added to the report structs — so the bindings and the CLI
compute the same reports from the same code path, and a drift between them shows
up as a compile error rather than a behaviour difference. `live.rs` is the only
genuinely new logic: the JS-object → `Event` mapping and the stateful class.

Three non-obvious things are needed to make the Cedar dependency tree compile to
`wasm32-unknown-unknown`, all captured in the crate:

- **Randomness backends.** Cedar/ahash/`uuid` pull in `getrandom`, which has no
  default backend on `wasm32-unknown-unknown`. The crate takes direct deps on
  `getrandom` 0.3 (`wasm_js`), `getrandom` 0.2 (`js`) and `uuid` (`js`) so
  feature-unification switches the whole graph to the JS-crypto backend.
- **`getrandom` 0.3 cfg.** It also needs `--cfg getrandom_backend="wasm_js"`,
  set in `.cargo/config.toml`.
- **`wasm-opt` features.** Rust/LLVM now emit bulk-memory and sign-extension
  ops; the `[package.metadata.wasm-pack.profile.release]` block passes
  `--enable-bulk-memory --enable-sign-ext …` so `wasm-opt` accepts them.

## Testing

`npm run verify` runs both suites (9 batch + 17 live assertions) and the
`--strict` type-check. All pass against `dogwood-language` at the commit this
was written for.

The load-bearing test for the live authorizer is **parity with `replay`**: one
scenario is driven twice — event-by-event through `DogwoodAuthorizer`, and as an
equivalent `.log` trace (rendered from the same event objects) through the
already-trusted `replay` — and the two verdict streams must agree on verdict,
timestamp and determining rules. That pins the part of `live.rs` that can
actually be wrong, the JS-object → `Event` mapping, without the suite having to
re-assert Dogwood's own temporal semantics.

The scenario is deliberately chosen to produce **both** allows and denies
(`deny allow deny deny`), and the test asserts that it does: a parity check
whose every verdict is `allow` would still pass with the temporal path dead.

Two things surfaced while writing it, both recorded here because they are the
kind of thing that silently produces a wrong test rather than a failing one:

- **`is_authorized` observes the event into history *before* deciding.** So a
  `request`-kind event is its own predecessor, and a policy whose clause is
  `formerly within 1h …request{}` is already satisfied on the very first call.
  Demonstrating that history accumulates therefore requires keying on a
  history-only kind (`response{}`), so the verdict can only flip because an
  earlier, separate call recorded one.
- **`EventBuilder::principal` inserts `callerPrincipal` into the logged record;
  the `.log` parser does not.** The parser treats `scope(...)` and the trailing
  logged record as independent. So a trace that is truly equivalent to a
  builder-built event must state `callerPrincipal` explicitly — which matters
  under the pinned default schema, where temporal predicates correlate on it.

## Notes & limitations

- Dogwood's own README stresses it is a **reference interpreter, not for
  production**; these bindings inherit that. They are for understanding the
  language, and for tooling and CI checks.
- The `net` feature (provider `http_get`) is **off** — it cannot work on
  `wasm32-unknown-unknown` and would make evaluation non-deterministic.
- The module is **8.7 MB** (9,134,780 bytes) with `wasm-opt -Os` applied —
  Cedar, rhai and the parser dominate. That is ~2.6 MB gzipped, which is the
  number that matters over the wire, but it is still a large dependency for a
  browser bundle; prefer the Node target for tooling and CI. (Adding the live
  authorizer grew it: exercising the entity store reaches more of Cedar's
  validation code, which dead-code elimination previously dropped.)
- One `DogwoodAuthorizer` is one temporal history. It is not thread-safe and
  holds state, so do not share an instance across unrelated principals if your
  event schema is unpinned — and remember to `free()` it (see above).
- A Rust panic surfaces as a readable `console.error` (a panic hook is installed
  on module load).
